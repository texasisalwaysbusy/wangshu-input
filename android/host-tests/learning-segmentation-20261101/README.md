# Pinyin personal-overlay separator investigation — NOT FIXED

`LearningSegmentationTest.java` invokes actual CandidateLearning with synthetic entries. It shows that pinning 仙 on `xian` makes it pinned for `xi'an`; red.txt records the failing desired isolation assertion. This is consistent with existing deliberate v1 behavior: the key normalizer strips apostrophes, and shared core/engine.cpp also strips them. Existing pinyin.tsv includes both 仙 and 西安 under `xian`. The UI screenshot requirement for a separator is not evidence that the present dictionary actually distinguishes syllable boundaries.

`OverlaySuppressionTest.java` uses actual CandidateLearning/CandidatePages with one synthetic overlay-only word. It shows an unconditional ban of personal overlay for split queries makes that existing candidate inaccessible in the split query even though its underlying record remains; suppression-red.txt intentionally fails the no-hiding assertion. The first run used a reversed test assertion and exited 0 despite demonstrating suppression; it was corrected before recording the red evidence. User asked not to hide existing personal data, so this mitigation is not implemented and no records were changed. To solve properly, preserve explicit boundaries in the engine and personal identities, devise transparent handling for ambiguous legacy v1 records rather than inventing their segmentation, and test search/ranking and real-device behavior. This is a feature/design gap, not a claim that old v1 violated its documented normalization contract.
