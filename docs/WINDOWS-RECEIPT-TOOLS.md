# Windows receipt tools / Windows 构建凭据工具

This is development-tool documentation, not evidence of an accepted Windows binary. Real-Windows registration, host compatibility and microphone acceptance remain incomplete.

这是开发工具说明，不是 Windows 二进制验收结果。真实注册、宿主兼容与麦克风验收仍未完成。

These tools read **schema 2** build receipts from the portable builder. They do
not select a compiler, download/install tools, register an IME, or publish files.
All destinations must be **new**, outside the source/build/runtime input roots.
Existing files, directories and dangling destination symlinks are rejected.
Failed or timed-out evidence is retained, never automatically deleted/retried.

## Source candidate, without runtime acceptance

```text
python tools/package_windows_personal.py --source-only --destination <new-source-package>
```

This creates `wangshu-ime-windows-source-candidate.zip` with the Windows build
sources, dictionaries, notices, relevant tests/tools and docs. It is not a full
Android checkout, a compiled release, or evidence of native runtime acceptance.
`CANDIDATE-STATUS.json` and `artifact.json` explicitly say SOURCE_CANDIDATE_ONLY
and compilation/native runtime NOT_RUN. Add `--verify-only` to inspect the source
manifest without writing an archive. No build receipt or runtime is needed.

## Runtime checks after genuine builds

Production and tests are separate builder runs with distinct new directories.
Do not combine/move their outputs or rewrite receipt roots. Both receipts must
refer to this exact source checkout and current complete build-input membership.

```text
python tools/run_windows_personal_checks.py --production-receipt <production>/source-attestation.json --tests-receipt <tests>/tests-source-attestation.json --android-fixture <existing-owned-synthetic-roundtrip.json> --android-fixture-sha256 <verified-SHA256> --destination <new-runtime-evidence>
```

On native Windows this runs the five existing attested x64 test executables
directly. On a non-Windows host an explicit existing trusted `--runner <path>`
is required. No legacy `run_wine.sh` is selected implicitly. A compatible
operator-managed Wine wrapper can be specified with `--path-style wine` and
`--wine-prefix <existing-initialized-prefix>`; this prepares Z: argument paths
and sets WINEPREFIX but does not initialize a prefix. The wrapper itself must
honor these inputs and must be separately trusted. No shell command expansion
or runner argument parsing occurs. A script runner must be directly executable.

Use `--verify-only` first for receipt/source/output/PE-header preflight with
**no process execution and no output creation**. `--timeout` defaults to 180
seconds per suite. On timeout the direct child is stopped by Python, but child
descendants may remain; inspect the owned processes before retrying elsewhere.

The runtime directory receives copies of the binaries, attested dictionary
data, and the hash-checked roundtrip fixture. LOCALAPPDATA, APPDATA, TEMP and TMP
are directed to new working directories. These are isolation conventions for
trusted code, **not an OS sandbox**. The original source/build outputs remain
read-only inputs. Test-created working data is retained and excluded from the
binary package. The Android fixture's bytes and format are not proof it was
generated by an actual Android run; preserve that provenance separately.

The suites are store (34), TSF editing (85), personal TSF (85 + 17), association
(16), and DLL loader/COM (17). TSF editing is repeated inside personal TSF, so
these numbers must not be summed as unique test cases. Each requires exit code
zero, exact complete summary lines, no FAIL line, and unchanged input/staged
hashes. The 16 association cases use mock TSF hosts, not real app integration.

`started.json`, per-suite records/raw logs and final `runtime.json` are written
once each. Missing/failed/interrupted suites do not receive a passing receipt.
Receipts bind the runner and the receipt-verifier implementation to their
current hashes. The compiler executable is not required again: its recorded
identity is checked for consistency, not independently rerun or rehashed.

## Binary development package

```text
python tools/package_windows_personal.py --production-receipt <production>/source-attestation.json --tests-receipt <tests>/tests-source-attestation.json --runtime <runtime-evidence>/runtime.json --destination <new-binary-package>
```

The unchanged installer needs **both x64 and x86 production pairs**; x64-only
builds may run x64 checks but are refused by this packaging mode. The archive
includes both architecture pairs, the built x64 voice helper, dictionaries,
notices, install/uninstall scripts, selected docs and runtime evidence. It does
not execute the scripts, bundle voice models/engine, or include private working
stores. Every ZIP member is rehashed and CRC-checked. Add `--verify-only` for a
no-write check. The runtime root and original runner must remain available for
validation; this is not a portable re-verification mechanism after relocation.

## Evidence limits and synthetic contract tests

The receipts are local unsigned records, not signatures or a defense against
someone rewriting all files and receipts. PE headers/hashes cannot prove genuine
compilation or execution. Only use a trusted real compiler and executor for
native acceptance. Headless/mock-host checks do not establish Windows GUI,
application integration, registration, x86 runtime, voice or microphone results.

```text
python -B tests/windows_receipt_tools_test.py
```

The Python tests create **synthetic header fixtures and a mock executor that
does not execute them**. They run with explicit `--synthetic-contract` tagging.
Those results cannot qualify for ordinary binary packaging. The package test
mode also requires that flag and creates only
`SYNTHETIC-CONTRACT-NOT-FOR-INSTALLATION.zip`, with a synthetic evidence kind.
All synthetic fixture roots, receipts and raw logs are labeled and retained.
No synthetic check is a MinGW, Windows, Wine or real TSF execution result.
